# LinguaType MVP 主链路实现卡

状态：`high_fidelity_frontend_merged`

当前产品输入固定为 A：雅思题目、完整全文和用户选择的目标句。本文只定义第一条可测试主链路，不扩展全文批改、自动替换、RAG、学习资产或第二条产品链路。

实现位置：`prototype/`。当前版本已把 L3/L4 更新为产品侧锁定 source 与路由、DeepSeek V4 Flash 只生成内容的 v7 完整版，并在核心链路外补齐本设备多篇作文、多句卡片、恢复、原创题库和自定义题目入口。OpenDesign 高保真前端已于 2026-09-04 合入当前项目。冻结 20 case 的原型 API 回归为 20/20 通过；1 名产品所有者完成过 1 次真实写作自测并获得正向定性信号，但这些证据仍不能证明外部用户价值或稳定英文质量。

## 先参考成熟做法

开源编辑器已经验证了三个适合复用的交互骨架：

- Tiptap 的 Bubble Menu 将操作入口锚定在当前文本选择附近，并允许通过条件控制何时出现。LinguaType 可借用“就近出现处理入口”的思路，但触发对象固定为含中文的完整目标句，而不是任意选区。
- ProseMirror 的 Decoration 可以给原文增加视觉标记而不改写文本；其社区案例也提醒，点击编辑器外的菜单可能导致选区或焦点丢失，因此 LinguaType 需要把目标句位置保存为显式状态，不能临时依赖光标。
- LanguageTool 的规则与建议系统把“发现位置”和“展示建议”分开。LinguaType 同样分离检测与支援，但每个帮助目标只提供一个英文，不采用多候选改写。

这些只是交互模式参考，不在本阶段锁定编辑器或前端技术。

## 主链路一句话

这条链路把用户作文中的一个中英混合目标句，与雅思题目和完整全文一起交给模型一次处理，转成直接表达或可逐个揭示的支架包；用户自行完成句子，系统只记录交互与反馈证据。

```text
L1 发现含中文句子
→ L2 用户选择并形成 A 输入
→ L3 本地校验与请求快照
→ L4 模型一次生成
→ L5 分层展示与本地揭示
→ L6 用户自行完成句子并反馈
→ L7 保存测试证据与 bad case
→ L8 再次发现新卡点，但不自动调用模型
```

## Step 3 / 3：主链路实现下钻

### L1 触发：发现含中文的句子

这一环节只负责发现潜在卡点并给用户入口，不判断用户真正想表达什么。

**输入可能来自两类情况：**

1. 用户正在编辑作文，新输入了一段中文占位。
2. 用户粘贴了一篇已经包含中文占位的作文。

**处理动作：**

1. 在本地检查作文中是否出现中文字符。
2. 按句子边界标记包含中文的句子。
3. 在句子附近显示“处理本句”，由用户主动点击。

**实现方式取舍：**

第一版用本地字符检查和基础句子边界规则就够，不调用模型做检测。检测只负责召回潜在目标句，误标时用户可以忽略。

**输出、状态和边界：**

输出一个或多个可选择的目标句位置，交给 L2。需要保存句子的起止位置和当时的文本版本，避免用户点击后因继续编辑而处理错句。句子边界不确定时，第一版允许用户手动确认整句；MVP 证据是中文占位能够被发现，且原文没有被修改。

### L2 输入：用户选择目标句并形成 A 输入

这一环节把产品已确认的 A 方案组装成一次请求。

**输入固定包括三项：**

1. `task_prompt`：雅思题目。
2. `full_essay`：当前完整作文。
3. `target_sentence`：用户明确选择的一个含中文句子。

**处理动作：**

1. 用户点击“处理本句”。
2. 系统读取点击时的题目、完整全文与目标句。
3. 创建本次请求快照，并锁定目标句在全文中的位置。

**实现方式取舍：**

第一版由用户分别输入题目和作文；目标句从作文中选择，不再让用户重复粘贴。没有题目或全文时不降级为 C，而是提示补齐输入。

**输出、状态和边界：**

输出一个完整 A 输入快照，交给 L3。需要保存 `request_id`、文档版本、三项输入和目标句位置。一次只能选择一个句子；目标句没有中文、已被用户修改或不再属于当前全文时，请求作废并要求重新选择。MVP 证据是每次模型调用都能追溯到唯一输入快照。

### L3 预处理：校验输入并准备单次调用

这一环节负责在调用模型前拦截明显错误，并建立后续协议检查所需的本地依据。

**输入可能有四种状态：**

1. 三项字段完整且目标句仍有效。
2. 题目为空。
3. 全文或目标句已变化。
4. 目标句包含一个或多个顶层中文片段。

**处理动作：**

1. 校验题目、全文和目标句非空。
2. 检查目标句确实来自当前全文且仍包含中文。
3. 按原文顺序提取顶层中文片段，作为响应覆盖检查依据。
4. 产品侧为每个片段锁定 `itemId`、`sourceZh` 与 `requiredAction`，再使用 v7 完整版 Prompt 和受控 schema 生成请求；不向模型提供评测分类或金标。

**实现方式取舍：**

第一版只用固定规则校验，不增加第二个模型判断节点。中文片段提取的目的仅是检查遗漏、乱序或虚构来源，不负责决定应该直给还是拆支架。

**输出、状态和边界：**

输出一个可调用请求和预期中文片段列表，交给 L4。保存 Prompt、schema 与模型版本。无法可靠定位中文片段时停止调用并记录预处理错误；MVP 证据是错误输入不会悄悄进入模型，评测金标也不会泄漏给生成端。

### L4 核心处理：模型一次生成结构化支架

这是第一版唯一必须使用 AI 的节点。帮助层级已由产品侧锁定，模型只生成英文表达或支架内容。

**输入包括：**

1. L3 通过校验的 A 输入。
2. v7 完整版 System Prompt。
3. v7 受控结构化输出约束。

**处理动作：**

1. 每个用户动作只调用模型一次。
2. 产品侧按当前固定路由为片段指定 `provide_expression` 或 `offer_scaffolds`，模型不得改动作。
3. 复杂片段在同次响应中默认准备 2 个、最多 3 个中文支架及隐藏英文；附属成分不得独立成项。
4. 返回后由本地合并 source 与动作，并校验覆盖、顺序、支架数量和粒度禁令。

**实现方式取舍：**

当前原型使用 DeepSeek V4 Flash 非思考模式与 v7 完整版 Prompt，不增加 Agent、RAG、模型路由、流式返回或自动重试。传输或结构失败时直接显示“本句暂时无法处理”，保留用户原文，并记录 bad case。

**输出、状态和边界：**

输出一个通过协议校验的内部结果，交给 L5。保存原始结构化响应、模型版本、调用耗时、错误类型和一次调用计数，不保存 API Key。遗漏、乱序、虚构来源、英文泄漏或结构无效时不向用户展示部分结果；MVP 证据是一次调用覆盖当前目标句，且失败不会改写作文。

### L5 输出：直接展示或渐进揭示

这一环节把同一模型响应投影成两种用户界面，同时保留用户的组句工作。

**输入可能有两类：**

1. `provide_expression`：一个中文片段对应一个英文表达。
2. `offer_scaffolds`：首屏只有 2—3 个中文语义支架，英文已生成但隐藏。

**处理动作：**

1. 直接项立即显示唯一英文表达。
2. 复杂项首屏只显示中文支架。
3. 用户可以依次揭示多个支架；已揭示英文保持可见。
4. 揭示只改变本地界面状态，不产生模型调用。
5. 不提供“一键应用”、自动替换或预先拼装答案。

**实现方式取舍：**

第一版使用目标句附近的轻量支援面板。面板与作文编辑状态分离，并使用 L2 保存的目标句位置，避免点击支架时丢失处理对象。

**输出、状态和边界：**

输出用户当前可见的表达支架，交给 L6。保存每个 `scaffoldId` 的揭示状态，不把隐藏英文写入首屏内容。用户继续修改同一句时保留原卡片与揭示状态，不显示“基于旧版本”，也不自动把结果接入新句子；只有整句被删除时，卡片才从界面移除并保留在导出记录中。MVP 证据是隐藏英文泄漏为零、揭示调用为零、原文自动修改为零。

### L6 反馈：用户自行完成句子并提供低成本判断

这一环节验证产品是否帮助用户继续写，而不是只验证模型能否返回英文。

**输入可能来自三类行为：**

1. 用户查看直接表达后继续编辑。
2. 用户揭示一个或多个支架后继续编辑。
3. 用户关闭结果、没有继续编辑或认为结果无帮助。

**处理动作：**

1. 用户自行移动、变形、连接或放弃支架。
2. 系统不判断用户必须使用哪个英文。
3. 本次处理结束时只询问一次“有帮助 / 没帮助”。
4. 选择“没帮助”后可选填：不准确、不自然、帮助过多、帮助太少、其他。

**实现方式取舍：**

第一版把行为记录与一句主动反馈结合起来。不能仅用“是否复制英文”判断价值，因为产品允许用户变形、重组或只借用部分表达。

**输出、状态和边界：**

输出本次帮助结果、用户反馈和处理后的目标句快照，交给 L7。内部测试需事先说明会保存作文片段；未取得同意时只保存交互计数，不保存原文。反馈缺失不自动记为失败；MVP 证据是能够区分“看到了输出”和“用户认为它帮助继续写作”。

### L7 状态沉淀：保存测试证据与 bad case

这一环节只为评测与复盘留证，不宣称个性化学习或自动进化。

**每次记录至少包括：**

1. 匿名测试会话与请求 ID。
2. 经同意保存的题目、全文、目标句和处理后目标句。
3. Prompt、schema、模型版本与内部结构化输出。
4. 直接项展示、支架揭示顺序、调用次数和错误。
5. 用户反馈与 bad case 标签。

**处理动作：**

1. 当前按作文保存在浏览器本地，并由用户主动导出结构化 JSON 记录。
2. 对失败记录做人工归类，不自动改 Prompt。
3. 将已确认问题加入回归样本候选；修改评测集时仍创建新版本，不回写冻结资产。

**实现方式取舍：**

当前所有作文与测试记录都只保存在本设备浏览器，不引入数据库。只有明确需要跨设备恢复或多人审核时，再评估持久化服务。

**输出、状态和边界：**

输出一份可逐次复盘的测试记录和 bad case 表，供产品判断下一轮是否继续。不得保存凭证、完整请求头或未经同意的作文内容；历史反馈不会自动改变下一次输出。MVP 证据是每个结论都能回到输入、输出、行为与用户反馈，而不是只看离线评分。

### L8 下一次触发：继续写作后发现新的卡点

这一环节把产品带回写作过程，但不扩展为主动代写或学习闭环。

**输入可能来自两类状态：**

1. 用户完成当前句后继续写，并出现新的中英混合句。
2. 当前作文没有新的中文占位。

**处理动作：**

1. 本地规则继续检测新的含中文句子。
2. 只显示新的“处理本句”入口。
3. 用户未点击时不调用模型、不弹出英文、不打断写作。

**实现方式取舍：**

第一版的“主动”只到低干扰提示为止。暂不做通知、能力画像、历史表达召回或自动推荐。

**输出、状态和边界：**

输出新的可选触发点并回到 L1。保存提示是否出现和用户是否主动使用；频繁误提示时允许用户关闭标记。MVP 证据是产品能随写作继续服务，同时模型调用权仍在用户手里。

## 已完成的最小证据闭环

### 第一阶段：接通可运行链路

1. 实现题目输入、作文编辑和含中文句子标记。
2. 接通 A 输入与当前 v7 单次结构化调用。
3. 实现直接展示、中文支架首屏和本地多次揭示。

### 第二阶段：补齐证据与失败边界

1. 保存输入快照、结构输出、揭示状态、错误和用户反馈。
2. 已用现有 20 个冻结 case 完成原型 API 回归，20/20 通过单次调用、固定路由、结构与首屏投影检查；界面仍保持零自动替换。
3. 产品所有者已完成 1 次真实写作自测；外部用户邀请暂缓，单次正向信号不外推为普遍效果。

### 第一轮需要取得的三类证据

- 链路证据：用户能从中文占位走到自行完成目标句，过程中没有被自动改写。
- 行为证据：能够记录处理触发、支架揭示、继续编辑和用户反馈。
- 风险证据：结构失败、帮助过量、语义偏差和无帮助结果都能被留存并复盘。

### 暂时不做

- 多候选表达、自动应用和完整句改写。
- 全文批改、评分、续写或观点生成。
- 登录、付费、多端同步和协作编辑。
- RAG、个人表达库、能力画像和自动学习。
- 后台主动调用模型或第二条产品链路。

## 原型完成定义

以下条件同时满足，才算“最小交互原型已接通”：

1. 用户能输入题目和完整作文，并选择一个含中文句子。
2. 每次处理只发送一次 A 输入并取得可校验的 v7 结果或明确失败。
3. 直接项立即显示；复杂项首屏不泄漏英文，揭示不再调用模型。
4. 系统从不自动修改作文，用户可以忽略、变形或组合支架。
5. 每次测试都能追溯输入版本、模型输出、揭示行为、最终句子和反馈。
6. 现有 20 个冻结 case 已通过原型级协议回归；这只代表链路正确，不代表真实用户效果。
