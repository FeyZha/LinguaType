# LinguaType 产品推导记录

> 目标：记录产品如何从一次真实跨语言表达卡点，逐步收敛为可验证的雅思写作 MVP。

## 1. 起点：雅思写作中的真实卡点

在一次雅思 Task 2 写作中，用户已经知道自己想表达“公众可达性”，却无法在句子 `It did develop ...` 中组织出合适的英文，只能暂停写作并搜索翻译，最后得到 `public accessibility`。

问题不在于“没有观点”，而在于中文意图与英文表达之间出现了断点：

```text
已有中文意图
→ 缺少可直接调用的英文表达
→ 离开写作页面搜索
→ 得到翻译结果
→ 仍不确定是否自然、能否接入原句
```

## 2. 问题定义：跨语言表达卡点

“审题—构思—组织—写作—检查”无法体现中文学习者的特殊困难。真正需要关注的是写作过程中的跨语言断点：用户会用中文占位、简化原意，或切换到翻译工具。

当前问题被定义为：

> 用户知道中文意思，但无法在当前英文句子中自然表达。

产品需要在不中断写作、也不替用户完成整句的前提下，提供足以继续写下去的英文表达支架。

## 3. 外部信号与证据边界

新航道文章[《如何提高雅思作文写作速度》](https://m.xhd.cn/news/99092388.html)提到，部分句式基础薄弱的考生会先用中文构句，再机械翻译成英文，导致写作变慢、错误增加和表达不自然。它能作为行业观察，但没有样本、研究方法和发生频率，不能当作用户研究结论。

结合用户本人的真实卡点与二语写作研究方向，目前只能判断：痛点有条件成立。尚未证明它在目标用户中普遍、高频，也未证明用户更偏好表达支架而不是完整翻译。

## 4. 用户需要什么程度的帮助

案例复盘表明：如果用户获得合适的英文表达块，就可能继续完成句子。但用户对原句结构也可能没有把握。

为了只验证一个核心假设，当前先解决中文意图到英文表达的语境化映射。句子校准、全文批改和能力训练不进入当前链路。

## 5. 产品锚点

**以雅思题目和全文为上下文，为任意一个中英混合句提供逐句、单结果、非代写式的英文表达支架。**

这一定义包含四个约束：

- 题目与全文只用于理解语境；
- 一次只处理一个目标句；
- 每个中文片段只返回一个表达；
- 用户自行决定如何完成句子。

## 6. 单一产品链路

1. 用户允许先用中文占位，继续写作。
2. 系统识别包含中文的句子，并提供“处理本句”。
3. 用户选择其中一句；模型读取雅思题目、全文和目标句。
4. 模型处理该句中的全部中文片段，每个片段只返回一个可接入原句的英文表达。
5. 用户根据支架自行完成句子；系统不自动改写原文。

这条链路只验证一件事：表达支架能否帮助用户跨过当前卡点，同时保留用户的写作主导权。

## 7. MVP 边界

当前明确不做：

- 完整句生成、整句改写和自动替换；
- 多候选选择；
- 全文批改、评分、续写和观点生成；
- 表达复盘、学习资产召回、RAG 和能力训练闭环；
- 同时验证第二条高频产品链路。

异常结果只保留低频记录入口，用于收集 bad case。

## 8. 成功标准

首轮评测关注三个维度：

- **语义正确**：理解中文意图，并符合题目、全文和目标句语境；
- **支架质量**：表达自然、能接入原句，且没有接管整句；
- **用户可继续性**：用户获得支架后能否自行完成句子。

新增观点、改变立场、遗漏中文、输出完整句、提供多个候选或格式不可用，均记为硬失败。baseline 运行前不预设准确率或提升比例。

## 9. 当前评测资产与证据边界

当前已冻结 `expression-scaffold.dev.v1`：20 条样本、25 个中文片段，覆盖常规、语境依赖、复杂混写和边界场景。

只有 `LT-ESC-001` 的中文卡点继承自真实经历，题目与全文为重建上下文；其余 19 条源自 AI 初拟并经过逐条静态复审。它们可用于检查模型能力，但不是真实用户数据。

当前尚无 baseline、模型分数、失败模式、改进幅度、真实用户测试或能力提升证据。

## 10. 下一步

1. 使用 `expression-scaffold-baseline-v1` Prompt 运行首轮 baseline；
2. 按三维标准评分，并人工复核硬失败、低分项和部分高分项；
3. 根据真实 bad case 总结失败模式；
4. 每轮只调整一个主要变量，在同一冻结评测集上复测；
5. 模型能力达到可用水平后，再进行小规模真实写作测试；
6. 根据验证结果决定是否进入应用实现。
