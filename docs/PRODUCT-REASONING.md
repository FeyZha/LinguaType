# LinguaType 产品推导记录

> 目标：记录产品如何从一次真实跨语言表达卡点，逐步收敛为可验证的雅思写作 MVP。

## 1. 起点：雅思写作中的真实卡点

在一次雅思 Task 2 写作中，用户已经知道自己想表达“公众可达性”，却无法在句子 `It did develop ...` 中组织出合适的英文，只能暂停写作并搜索翻译，最后得到 `public accessibility`。

问题不在于“没有观点”，而在于中文意图与英文表达之间出现了断点：

```text
已有中文意图
→ 缺少可直接调用的英文表达
→ 离开写作页面搜索
→ 得到翻译结果
→ 仍不确定是否自然、能否接入原句
```

## 2. 问题定义：跨语言表达卡点

“审题—构思—组织—写作—检查”无法体现中文学习者的特殊困难。真正需要关注的是写作过程中的跨语言断点：用户会用中文占位、简化原意，或切换到翻译工具。

当前问题被定义为：

> 用户知道中文意思，但无法在当前英文句子中自然表达。

产品需要在不中断写作、也不替用户完成整句的前提下，提供足以继续写下去的英文表达支架。

## 3. 外部信号与证据边界

新航道文章[《如何提高雅思作文写作速度》](https://m.xhd.cn/news/99092388.html)提到，部分句式基础薄弱的考生会先用中文构句，再机械翻译成英文，导致写作变慢、错误增加和表达不自然。它能作为行业观察，但没有样本、研究方法和发生频率，不能当作用户研究结论。

结合用户本人的真实卡点与二语写作研究方向，目前只能判断：痛点有条件成立。尚未证明它在目标用户中普遍、高频，也未证明用户更偏好表达支架而不是完整翻译。

## 4. 用户需要什么程度的帮助

案例复盘表明，“给对英文”不等于“给对帮助量”。词或短语可以直接给一个英文块；如果中文已经是一条完整命题，整段翻译即使正确，也会让用户几乎不再做语言组织。

因此当前采用分层帮助：先判断中文片段是具体表达卡点，还是包含多个潜在卡点的完整命题。前者直接支援；后者在同一次模型响应中预生成多个最小支架，但界面先只展示中文，用户点击后才本地揭示对应英文。句子校准、全文批改和能力训练仍不进入当前链路。

## 5. 产品锚点

**以雅思题目和全文为上下文，为任意一个中英混合句提供逐句、单结果、分层且非代写式的英文表达支架。**

这一定义包含四个约束：

- 题目与全文只用于理解语境；
- 一次只处理一个目标句；
- 每个当前帮助目标只返回一个英文表达；
- 完整命题拆成多个最小语义支架，英文随首轮预生成但按需揭示；
- 用户自行决定如何完成句子。

## 6. 单一产品链路

1. 用户允许先用中文占位，继续写作。
2. 系统识别包含中文的句子，并提供“处理本句”。
3. 用户选择其中一句；模型读取雅思题目、全文和目标句。
4. 产品侧锁定中文片段与帮助动作，模型只运行一次：直接项给一个英文表达；复杂项默认生成 2 个、最多 3 个“中文语义支架 + 对应英文”的内部支架包。
5. 界面初始只展示中文支架；用户可依次选择多个，本地揭示对应英文并保持已揭示内容，不再次调用模型。
6. 用户自行取舍、移动、变形、连接和接入支架并完成句子；系统不自动改写原文。

这条链路只验证一件事：表达支架能否帮助用户跨过当前卡点，同时保留用户的写作主导权。

## 7. MVP 边界

当前明确不做：

- 完整句生成、整句改写和自动替换；
- 翻译完整命题，或把多个支架预先组装成完整答案；
- 多候选选择；
- 全文批改、评分、续写和观点生成；
- 表达复盘、学习资产召回、RAG 和能力训练闭环；
- 同时验证第二条高频产品链路。

异常结果只保留低频记录入口，用于收集 bad case。

## 8. 评测成功标准（v4）

v4 把评测拆成三个检查点：

- **一次生成**：20 个 case 是否各用一次响应覆盖全部片段并生成完整内部支架包；
- **渐进揭示**：复杂项首屏不泄漏英文，点击一个或多个支架均不产生模型调用；
- **组合边界**：每个英文是否忠实自然，整组是否可组合但仍保留实质组句工作。

每个顶层中文片段单独评价语义保持、支架质量、帮助剂量和用户可继续性；一条 case 的结论取最差 item，不用平均分遮住局部失败。正常的词序移动、词形变化、冠词或介词补充属于用户练习，不自动扣分。

聚焦项必须可追溯到原中文含义，但不要求机械复制连续原文；轻量语义归纳只要不新增观点、不改变立场、关系或范围即可。遗漏或乱序顶层片段、聚焦阶段泄漏英文、一次给齐完整命题、同一帮助目标给多个英文候选或格式不可用，仍记为硬失败。baseline 运行前不预设准确率或提升比例。

## 9. 当前评测资产与证据边界

当前已冻结 `expression-scaffold.dev.v1`：20 条样本、25 个中文片段，覆盖常规、语境依赖、复杂混写和边界场景。

只有 `LT-ESC-001` 的中文卡点继承自真实经历，题目与全文为重建上下文；其余 19 条源自 AI 初拟并经过逐条静态复审。它们可用于检查模型能力，但不是真实用户数据。

当前只保留 LongCat-2.0 的最终 v1 LangGraph 结构化输出运行 `baseline-20260820-longcat-2.0-langgraph-structured`。20 条均得到 output，旧 Judge 预评为 13 pass、6 needs improvement、1 bad case。

人工规则复核发现，v1 把连续中文拆分视为结构错误，却允许完整分句直接翻译；同时要求原位替换，并用“改动越少”衡量可继续性。这些规则会惩罚合理的自主组句、奖励完整答案。因此旧结果只作为 v1 历史证据保留，不能迁移成 v2 的模型结论。

`expression-scaffold.dev.v2` 已冻结 15 个直接表达与 10 个先聚焦片段。LongCat-2.0 共执行 20 次初轮与 10 次离线聚焦探针，30 次均取得响应。用户否决 LongCat-2.0 同模型 Judge 后，项目改由 3 个 Codex 子 Agent 隔离审核原始输出并裁决分歧；用户再对全部 7 个非通过项完成人工校准。最终离线分布为 29 pass、5 needs improvement、1 bad case，20 case 取最差项为 15/4/1。`LT-ESC-005` 从机器 bad case 覆盖为人工 pass：用户确认小粒度中文语义支架正是产品的最小可用单元，因此 v2 的直给动作金标和连续子串规则过严。另发现 `LT-ESC-014/015/016` 各有一个 selected-focus 探针无法从本次 initial 输出点击到达。

`expression-scaffold.dev.v3` 据此改为 14 个直接表达与 11 个先聚焦片段，允许可追溯的非连续语义单位，并从本次 initial 的真实选项确定性选择第一项运行二轮。LongCat-2.0 的 20 次 initial 中 18 次结构可用、2 次协议失败；实际产生的 9 次 selected-focus 均完成。三个隔离 Codex 子 Agent 预审 34 个 item/阶段为 29 pass、3 needs improvement、2 bad case，当前仍待用户人工校准。以上各版离线结果都不能代替真实写作效果。

`expression-scaffold.dev.v4` 保留 v3 的 14 / 11 路由与语义口径，但把两阶段生成改为一次生成内部支架包、界面本地渐进揭示。LongCat-2.0 首次 baseline 的 20 次调用全部通过结构与协议校验，共返回 14 个直接项、11 个支架包和 27 个支架，首屏英文泄漏为 0。

随后完成 DeepSeek V4 Flash 的速度、成本、Prompt 与控制边界验证。用户在 v6 人工审核中确认整体可接受，并指出“可能”“同时”不应独立成为支架；v7 据此把复杂片段收紧为默认 2 个、最多 3 个支架，并由产品侧锁定 source 与动作。用户最终选择 v7 完整版，暂停流式返回与精简 Prompt。更新后的内部原型用冻结 20 case 运行真实 API 回归，20/20 通过结构、固定路由、单次调用和首屏投影检查，P50/P90 约为 1.08/1.69 秒。该结果不替代英文质量与真实写作效果审核。

随后以该全文 baseline 为 A，只改变 `full_essay` 的实际取值，运行 B 相邻窗口与 C 仅目标句。B/C 分别有 19/20、18/20 个 case 通过协议；三路隔离 Codex 盲审为 A 13/4/3、B 14/2/4、C 8/3/9。B 对 C 有 6 个 case 更好且没有更差，C 因此不进入下一轮；A 与 B 只有 5 个 case 出现方向差异，结果混合。用户最终确认沿用 A，并关闭 B/C 复测方向。该选择是为了收敛产品输入，不改变实验的证据边界，也不代表全文价值、成本或真实体验已经被证明。
