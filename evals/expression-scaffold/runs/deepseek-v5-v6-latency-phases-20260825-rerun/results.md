# DeepSeek v5 / v6 分段延迟诊断

## 结论

v6 多出的时间主要发生在 L4“模型继续生成结构化支架内容”，不是产品侧路由、本地合并或最终校验。减少无意义的细碎支架有望同时改善质量与速度。

## 原始非流式 9 case 现象

| 指标 | v5 | v6 | v6 - v5 |
| --- | ---: | ---: | ---: |
| 平均完整返回时间 | 1,024.2ms | 1,365.6ms | +341.4ms |
| P50 | 954ms | 1,295ms | +341ms |
| P90 | 1,748ms | 2,084ms | +336ms |
| 平均输入 token | 1,362.7 | 1,142.0 | -220.7 |
| 平均输出 token | 123.8 | 158.8 | +35.0 |

9 条中 8 条 v6 更慢。但仅凭各一次调用，无法区分模型阶段和服务波动。

## 本地处理微基准

使用已保存输出重复执行解析、合并和协议校验：

| 本地步骤 | 平均耗时 |
| --- | ---: |
| v5 解析 + 校验 | 0.0187ms |
| v6 解析 + 本地合并 + 校验 | 0.0357ms |
| v6 新增开销 | 0.0170ms |

本地控制逻辑无法解释数百毫秒差异。

## 重复流式分段测速

选择一个简单直接 case、一个混合 case、一个多片段复杂 case；v5/v6 各预热一次后，每个 case 交错重复 3 次，共 9 次有效计时/版本。该测试把一次响应分为请求准备、首内容等待、后续生成和本地完成。

| 阶段均值 | v5 | v6 | v6 - v5 |
| --- | ---: | ---: | ---: |
| 请求准备 | 1.502ms | 1.900ms | +0.398ms |
| 响应头等待 | 91.842ms | 94.841ms | +2.999ms |
| 首个有效内容 | 882.757ms | 736.661ms | -146.096ms |
| 首内容后的流式生成 | 543.115ms | 789.015ms | **+245.900ms** |
| 模型服务总阶段 | 1,425.872ms | 1,525.675ms | +99.803ms |
| 本地解析/合并/校验 | 0.099ms | 0.145ms | +0.046ms |

首内容等待波动较大，v6 没有稳定地更慢；最稳定的额外耗时发生在首内容之后的生成阶段。

## 按复杂度拆分

| Case | 类型 | v6 首内容变化 | v6 生成阶段变化 | v6 服务总时间变化 | 平均输出 token 变化 |
| --- | --- | ---: | ---: | ---: | ---: |
| LT-ESC-002 | 简单直接 | +105.1ms | +83.9ms | +189.0ms | +5.0 |
| LT-ESC-013 | 直接 + 复杂 | -227.3ms | **+304.8ms** | +77.5ms | +49.3 |
| LT-ESC-016 | 多片段复杂 | -316.1ms | **+349.0ms** | +32.9ms | +48.7 |

复杂 case 的额外时间集中在输出更多嵌套支架字段，而不是开始推理之前。

## 为什么 v6 会生成更久

1. v6 由产品侧锁定复杂动作，模型不能像 v5 那样把部分复杂片段直接整段返回。
2. 复杂支架需要重复生成 `scaffoldId`、`focusZh` 和英文表达，输出 token 增加。
3. 当前 v6 仍会生成“同时”“可能”等低价值独立支架，既增加输出，又降低产品质量。
4. API 服务本身存在明显波动；重复流式测试中 v6 服务总阶段只平均多约 100ms，因此原始单次 +341ms 不能全部解释为 v6 固定开销。

## 流式边界

流式诊断中 v5 为 9/9 结构有效；v6 为 6/9，三个失败均来自 `LT-ESC-013` 把 `recommendedExpression` 返回为 `expression`。非流式 v6 原实验为 9/9。当前不应为了感知速度直接切换流式工具调用；该结果只用于拆解时间阶段。

## 下一版建议

1. 复杂支架默认 2 个；只有存在第三个独立实义单位时才允许 3 个，暂不允许 4 个。
2. 连接词、情态词、程度词和结构助词不得独立成支架，必须吸收到相邻实义支架。
3. 先复测 `LT-ESC-016`、017，再回归 9 个定向 case。
4. 保持非流式、零自动重试；不要用流式掩盖实际耗时。

## 证据边界

分段测速只覆盖 3 个代表 case、每版 9 次有效流式计时；它足以排除本地合并为主要原因，并定位额外时间主要在生成阶段，但不能证明长期稳定延迟或真实用户感知。
